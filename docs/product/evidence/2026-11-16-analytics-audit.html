What can be measured today?

Adoption goal: no

The agreed goal is ten engineers besides the owner using a personal learning map in at least two separate weeks by 6 January 2027. Traffic counts do not establish meaningful use, identity across weeks, or target-audience membership.

Goal reported in PRODUCT.md, 11 November 2026. Instrumentation gaps observed in source; meaningful-use proxies still require validation.

Funnel constraint: partly

Reach is visible through pageviews and sessions. Tour engagement, saved progress, search success and personal-map return use are not reliably measurable with current custom tracking.

The local catalog includes existing uncommitted development work. Its production deployment was not verified; the live Zernio profile and Rybbit script were verified by HTTP reads.

Suggested first wave: six event types.

Fix the shared adapter; add tour_started, tour_step_viewed, tour_end_reached, tour_exited, progress_changed and map_used. Add search, learning-link and setup-copy outcomes only in the next wave. No tracking code or agent instructions were changed by this audit.

Target tracking plan

These are proposed schemas, not live events. Use fixed snake_case names, flat allowlisted string/number properties, and numeric 0/1 if a flag is needed. Source tags and IDs describe public content, not a learner’s private map.

Eligible profile visit→Tour started→Step viewed→End reached / explicit exit→Map used / progress saved

Shared Tour context

tour_id (e.g. zernio or mamitsu), tour_version, attempt_id, layout and total_steps. Pass a stable profile/tour ID into QuickTour explicitly. Give a new attempt an ephemeral ID; preserve it with the resume state for a same-visit skill-page round trip. An explicit restart gets a new attempt. This ID must not become a cross-visit user identifier.

Emit started once per activation episode (new, resume, restart or hash restoration); count unique attempts for start-to-end analysis. A resumed attempt can emit another started event with start_type=resume. Deduplicate end events by attempt; deduplicate step coverage by attempt + step. Preserve the attempt’s viewed-step set when resuming.

Centralize Tour emission in state transitions and outgoing-action handling. Forward the input method from every path; do not attach separate analytics to Next, arrows and swipes that all invoke the same transition. A link’s middle/modifier-click handling should avoid counting both a central handler and an element handler.

Optional later events and events to avoid

If visible exposure becomes a real question, add tour_available once the inline Tour or mobile start surface is actually visible. Until then, call the denominator “eligible profile visits,” not “people who saw the Tour.”

If login or agents become a priority, instrument confirmed backend outcomes such as sign_in_completed, agent_authorized and agent_tool_used, with fixed provider/tool names and success only after the server knows it happened. Link browser/server identity only through a designed mechanism; server host/IP must not become a visitor identifier. Instrument sync reliability separately from a user’s local progress change. None of these are required for the first six events.

Skip theme changes, map animation frames, hover/pointer movement, every keystroke, automatic illustration replays and generic “button clicked” clones. Do not add a custom pageview where Rybbit already collects one. Keep Random skill, sign-out and revocation diagnostics only when a concrete decision uses them.

Counting rules and privacy details
  • Tour start-to-end uses attempts grouped by their first start, with the same reporting cutoff and content version. At small volumes, report counts such as 3 of 12, rather than precise percentages. Separate new/resumed attempts and inline/full-screen entry.
  • An end card means the end was reached. Full coverage means all distinct skill cards were shown, not necessarily read. Missing final events can mean a closed tab, ad blocking or interruption. Treat these as unknown outcomes, not a confirmed exit reason.
  • Compare onward exploration after a Tour with other visits descriptively. It does not prove the Tour caused the difference. Do not sum raw outbound and learning_link_opened as two conversions.
  • Progress changes are a behavioral proxy, not competence or proof of learning. The goal requires same-person use in separate Monday–Sunday weeks in Europe/Madrid, excluding owner/test traffic. No current identity mechanism proves that automatically.
  • Keep raw search strings out of custom properties. Because the catalog stores q in the URL and live Rybbit tracks query parameters, suppress q in analytics URL collection before claiming search terms are excluded. Preserve approved UTM parameters through an explicit allowlist. Replay may capture full URLs independently; review its handling separately.
  • Do not transmit email, name, personal-map contents, OAuth codes/state, access tokens, arbitrary error text or copied commands. IDs for public skills/resources are acceptable context; private per-skill statuses need collection copy aligned before use. Avoid identifying users solely to count anonymous Tour interactions.
  • The deferred SDK needs a bounded, single-drain queue or supported readiness handling so early actions are not silently lost. It must remain harmless when disabled or blocked, and opt-out must suppress events rather than indefinitely queue them.

Implementation acceptance checks

  1. Exercise both Tours on desktop inline and mobile full screen, plus chapter/map jumps, keyboard, swipes, dock entry, resume, hash restoration, explicit close and outgoing links. Confirm semantic starts in each eligible path and no new start on expansion alone.
  2. Assert an event for each actual card transition, a single end event per attempt, preserved distinct-card coverage on resume, and a fresh attempt on explicit restart. Check last-step context before mobile reset.
  3. Mark a single skill and a bulk group; repeat the same action; restore from account state. Expect only real user changes, correct changed_count, and no synthetic changes from rehydration.
  4. Test a delayed, blocked and absent SDK. Verify local/staging/agent runs cannot reach the production collector. Confirm opt-out and failure do not break the product.
  5. On a separate test site, verify exact event names, string/number property types, order and single receipt in Rybbit’s received-event API. Inspect collected URLs/replays for excluded q, auth codes/state and sensitive account content. A local spy pass alone is insufficient.
  6. When first deployed, compare received custom event names with this plan before building funnels. If backend identity is later introduced, test login, logout, account changes and cross-device mapping separately.

Draft guidance for future agents

Proposed for the website repository’s agent instructions when you choose to add it. This audit has not created or modified an AGENTS.md file.

For every new or changed user-facing feature, decide whether existing Rybbit events can answer adoption, success and failure/drop-off questions. Add or update semantic events only where there is a concrete measurement gap, using the shared tracking adapter and the tracking plan. Fire from the state transition or confirmed outcome, cover keyboard/touch/resume paths, and prevent duplicate or no-op events. Use fixed event names and small, allowlisted properties; omit credentials, personal details, free text and complete personal-map data. Keep development, staging and agent tests out of the production collector. Verify event name, properties and single delivery in an isolated local sink or test site, and record the event change—or why no new event is needed—in the implementation summary.

Primary Rybbit documentation checked for this audit

  • Track Events: the browser custom-event API is window.rybbit.event(name, properties); data attributes are also available. Prefer semantic transition calls for the Tour so keyboard and touch have the same measurement.
  • Autocapture: outbound, button and form capture are separate capabilities. Autocaptured button text does not define a saved or completed outcome.
  • Tracking script: script configuration, query/fragment handling, readiness-related integration context and replay privacy controls. Installed config, rather than current documentation defaults, is the evidence for this site.
  • Identify users: persistent signed-in identification and clearUserId() are explicit APIs; they are not implemented in this site today.
