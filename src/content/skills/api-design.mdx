## Why it matters for a product engineer

An API is a contract that other people's code depends on. Once it is used, every change can break
someone, so the first design matters more than in most code. For a developer product the API is the
product: its names, errors and limits are the user experience.

## How to do it

1. Start from what the caller wants to do, and model the resources they think in, not your database
   tables.
2. Use a few standard methods on each resource (list, get, create, update, delete) and the same
   naming everywhere.
3. Return errors that say what went wrong and how to fix it, with a stable code a program can read.
4. Add pagination, rate limits and idempotency keys from the start. They are hard to add later.
5. Plan for change: add fields instead of changing them, and version only when you must.
6. Write the documentation and one working example before you ship, and try them as a new user.

## Common mistakes

- Exposing the database schema as the API.
- A different shape for each endpoint, so callers learn every one separately.
- Errors like "Something went wrong" with no code.
- Breaking changes without warning or a migration period.
- Building features in the dashboard first and adding the API later.

## Example

Zernio is an API first. "Most features we no longer build for the UI, only for the API", Miquel
Palet said, and the site states the rule: if it is not in the API, it does not ship. One posts
endpoint covers every network. Analytics are stored and refreshed on Zernio's side, so one call
returns a week across all of a user's accounts. ([Zernio in In practice](/in-practice/zernio/))
