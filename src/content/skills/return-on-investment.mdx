## Why it matters for a product engineer

Every piece of work costs time, money and attention, and it should return more: revenue, lower costs
or time saved. This is true for features, infrastructure and internal tools. Rough estimates are fine.
What matters is checking the real return afterwards, so the next estimate is better.

## How to do it

1. Write the expected return in one unit: money per month, hours saved per week, or customers kept.
2. Write the full cost: building it, running it, maintaining it, and the attention it takes.
3. Estimate how long it takes to pay back, and how confident you are in each number.
4. Prefer small bets with a short payback and a clear way to check.
5. Set a date to check the real return, and a rule for when to stop.
6. Compare with the alternative: the best other use of the same time.

## Common mistakes

- Counting the cost of building and forgetting the cost of running and maintaining.
- Estimating once and never checking.
- Precise numbers built on guesses.
- Ignoring internal tools because their return is time, not revenue.

## Example

After our call, Mamitsu's maker set up an agent that reads the week's extractions and reports every
Monday. At the current traffic it costs little. Its return is counted in problems and new uses that
each report shows and that the maker did not already know. It also has a rule for stopping.
