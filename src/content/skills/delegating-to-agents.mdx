## Why it matters for a product engineer

More and more code, research and testing is done by agents, and the result depends on how the work
was handed over. A good brief for an agent looks like a good ticket for a person: the goal, the
context, the limits and a way to check the result. Writing that brief, and checking what comes back,
is quickly becoming a core engineering skill.

## How to do it

1. State the goal as an outcome, not a list of steps.
2. Give the context the agent cannot find alone: who the users are, what to ignore, decisions
   already made.
3. Set the limits: what it may change, which tools it may use, where the result should go.
4. Give it a way to check its own work: tests, a command to run, screenshots to compare.
5. Ask for a short report: what it did, what it could not do, what needs a decision.
6. Review the result as you would a colleague's, and turn every correction into a rule for next time.

## Common mistakes

- A one-line request for a large task.
- No way for the agent to check the result, so it reports success without proof.
- Leaving out a limit that seems obvious to you.
- Accepting work you cannot explain or maintain.

## Example

On 18 November, RelievApp's maker asked an agent for ten different interactive experiences. The
brief had a goal, criteria, a range to explore and a deliverable. In 38 minutes the agent built ten
working prototypes, tested them at phone size and wrote up the pros and cons. One thing was missing:
where the result should go. The rule came after, and is now in every agent's instructions.
