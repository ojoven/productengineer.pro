## Why it matters for a product engineer

Every system depends on parts that will fail: a database, a cloud service, a payment provider, an AI
model. Without limits, one slow part makes callers wait, retries add more load, and the failure spreads
to everything else. Timeouts, retries with backoff, circuit breakers and fallbacks keep one failure in
one place. Product engineers also decide what users see when a part fails: a clear message and the
features that still work, or a blank screen.

## How to do it

1. List each dependency, and decide what the product does when it is slow or down.
2. Set a timeout on every outside call, shorter than the time the user will wait.
3. Retry only safe operations, with backoff and jitter, and cap the total number of retries.
4. Limit incoming work when queues grow, and reject extra requests early instead of failing slowly.
5. Test failures on purpose: block a dependency in staging, and check what users see.

## Common mistakes

- No timeout, so one slow service holds every thread.
- Retries at every layer, which multiply the load on a struggling service.
- Recovery processes that were never tested at full scale.
- An error page for the whole product when one optional feature fails.

## Example

On 19 October 2025, a race condition in AWS automation left the DNS record for DynamoDB's main endpoint
in Northern Virginia empty. DynamoDB itself recovered within three hours, but the failure spread. The
system that manages EC2's physical servers had to renew a huge number of leases. The work timed out,
was queued again, and the system went into congestive collapse. Engineers recovered it by limiting
incoming work and restarting hosts. AWS is adding rate limits based on queue size.
