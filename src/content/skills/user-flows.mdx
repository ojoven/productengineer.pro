## Why it matters for a product engineer

A user flow is the steps, branches and end states of one task. It is close to how engineers already
think about state machines. Drawing it before you build shows the missing states, the dead ends and the
steps that do not need to exist, when changing them still costs nothing.

## How to do it

1. Pick one task with a clear start and a clear end, such as "cancel a subscription".
2. Write the entry points: where people start the task from.
3. Draw each step and each decision. For every decision, draw every branch, not only the happy one.
4. Add the states engineers usually discover late: loading, empty, error, no permission, offline.
5. Mark the end states, and check that each one leaves the user knowing what happened.
6. Remove the steps that add nothing, then build from the diagram and keep it next to the code.

## Common mistakes

- Drawing only the happy path.
- Forgetting the emails, notifications and other channels that are part of the flow.
- Steps that exist because the data model needs them, not the user.
- A flow drawn once and never updated after the code changes.

## Example

In Papermark, clicking "cancel" does not end in a cancellation. The flow offers a pause: three months
at $0, with every link still working. Three days before billing resumes, an email says so. If a
visitor opens a paused team's data room, the team gets an email that someone visited, with the details
waiting until they unpause. ([Papermark in In practice](/in-practice/papermark/))
