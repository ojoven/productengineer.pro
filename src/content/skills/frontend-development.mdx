## Why it matters for a product engineer

The frontend is where most product decisions become visible: the layout, the words, the states and the
speed. A product engineer who can build it well can test an idea with real users the same week, and
can see problems that a design file hides, such as a slow network, a long name or a keyboard user.

## How to do it

1. Start from HTML that works on its own: real links, real forms, real buttons. Then add CSS, then
   JavaScript to improve it.
2. Build every state, not only the happy one: loading, empty, error, partial data and no permission.
3. Use the platform before a library. A native `dialog`, `details` or form validation often does the
   job.
4. Test on a real phone, on a slow network and with the keyboard, before you call it done.
5. Keep components small and named after what they mean in the product, not how they look.
6. Measure what users get: load time, layout shifts and errors in the browser, from real visits.

## Common mistakes

- A page that shows nothing until all the JavaScript has run.
- Only the happy path built, with errors left as a blank screen.
- Testing only on a fast laptop with a fast connection.
- A new dependency for something the browser already does.

## Example

In 2013, GOV.UK's team wanted to know how many people use the site without JavaScript. They added
three tiny images to the home page and counted the requests in over half a million visits. About 1.1%
of visits did not run JavaScript. Most of them had it switched on, but the script did not run, for
reasons such as network errors or browser add-ons.
