## Why it matters for a product engineer

A page that is fast on a developer's laptop can be slow on a cheap phone over a mobile network. Lab
tests run on known machines, so they miss what many real users experience. Real user monitoring
measures speed and errors on the devices people actually use, and error tracking groups crashes so the
most common ones stand out. Product engineers can then fix the problems that affect the most users.

## How to do it

1. Collect Core Web Vitals from real users, with device type, browser, country and page.
2. Look at the 75th percentile, not the average, and split it by device and connection.
3. Track client errors with an error tracker that groups them and shows how many users each affects.
4. Connect performance and errors to the release, so you can see which change made things worse.
5. Use lab tests to debug a problem that field data found, not instead of field data.

## Common mistakes

- Judging speed by a lab score on a fast machine.
- One average across desktop and mobile.
- Hundreds of error types with no grouping and no owner.
- Ignoring responsiveness after the page has loaded.

## Example

The Web Almanac uses real-user data from Chrome to measure the web each year. In 2024, 54% of websites
had good Core Web Vitals on desktop, but only 43% on mobile. That year, Interaction to Next Paint
replaced First Input Delay as the responsiveness metric. With the older metric, 48% of sites would have
passed on mobile. The new one measures more of each visit, so it found problems that the old metric
missed.
