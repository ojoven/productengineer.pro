## Why it matters for a product engineer

Authentication is the door to every account. It is easy to get subtly wrong, and one mistake exposes
everything behind it. It is also the first friction in the product: every rule on a signup form
loses some people. A product engineer decides both sides, the security and the experience.

## How to do it

1. Use a proven service or library. Prefer sign-in without a password: passkeys, or a provider
   people already use.
2. If you keep passwords, follow NIST: ask for length, not a mix of characters. Accept long
   passwords, spaces and Unicode, and allow paste, so password managers work.
3. Compare each new password with a list of breached and common passwords, and say why you reject
   one.
4. Store passwords with a slow, salted password hash, such as Argon2id or bcrypt.
5. Limit failed attempts, and offer a second factor.
6. Use the same generic message for a wrong user name and a wrong password, at sign-in and at
   password reset.

## Common mistakes

- Rules for symbols and digits. NIST notes that people respond to them in very predictable ways.
- Forced password changes every few months.
- Security questions, such as the name of a first pet.
- Writing your own session or token logic.
- A signup form that asks for a password before the person has seen any value.

## Example

NIST asks for a check against breached passwords, but sending a password to an outside service is a
new risk. Cloudflare and Troy Hunt's Pwned Passwords solved this with k-anonymity. The site hashes
the password with SHA-1 and sends only the first 5 of the 40 hexadecimal characters. The service
returns every breached hash that starts with them, about 478 on average, and the site compares them
itself. The password, and even its full hash, never leave the site.
