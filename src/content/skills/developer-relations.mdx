## Why it matters for a product engineer

Developers trust working code more than marketing. For a product that developers use, the docs, the
examples, the open-source code and the answers in a forum are the sales team. Product engineers are
the most credible people to do this work, because they can show how something is built and why.

## How to do it

1. Start with the developer experience: a quick start that works in minutes, and docs that answer
   real questions.
2. Write about how you built things, with code people can copy. Each post should solve a problem for
   the reader.
3. Be where developers already are: GitHub, forums, the communities of the tools you build on.
4. Answer every question in public, so the next person finds the answer.
5. Bring what developers say back into the product: bugs, missing features, confusing docs.
6. Measure what developers do: projects created, first API calls, contributors, not only followers.

## Common mistakes

- Marketing copy in developer docs.
- Samples that do not run.
- Talks and posts with no link to a first step in the product.
- Treating developer relations as events, and ignoring the docs.

## Example

Papermark's co-founder built it in public. After the first weekend version, he spent the next
weekends on features and wrote six posts on dev.to on how he built each part, with the code open.
"Six dev.to posts moved the project further than any single launch tweet." Zernio, an API, offers
Ayrshare's users an SDK with the same method signatures, so switching takes few changes.
([Papermark](/in-practice/papermark/), [Zernio](/in-practice/zernio/))
