## Why it matters for a product engineer

Without a plan, teams track everything and still cannot answer the question that matters. A tracking
plan starts from the questions, then lists the events and properties that answer them. It is also
the spec a product engineer implements, tests and reviews against, so the data means the same thing
to everyone who reads it.

## How to do it

1. Write the questions first: what will you decide, and what would you need to see to decide it?
2. For each question, list the events: one name per user action, in one naming pattern, such as
   object and action.
3. Define each property: its type, its allowed values, and an example.
4. Say exactly when each event fires: on the click, or when the server confirms the action.
5. Give every event an owner, and keep the plan in the repository, next to the code that fires it.
6. Review changes to the plan like code. Remove events that answer no question.

## Common mistakes

- Tracking every click "just in case".
- Names that change from one team to the next: "Sign up", "signup", "User Signed Up".
- A plan in a spreadsheet that the code no longer matches.
- Properties that carry personal data by accident.

## Example

At GitLab, each event is defined in a file in the repository, created with a command-line tool.
Names follow one pattern, an action, its target and where it happens, such as `create_ci_build`.
GitLab's analytics team now also runs agents for this work. One turns a tracking idea into an
issue, one writes the definitions, code and tests, and one reviews instrumentation changes when a
merge request is ready for review.
