## Why it matters for a product engineer

An API key in a repository works for anyone who finds it. Products depend on more keys every year:
payments, email, analytics, model providers, agents. Each new integration adds one. A product
engineer who handles keys well limits what one leak can do, and can replace a key in minutes, not
days.

## How to do it

1. Keep secrets out of code, prompts and logs. Load them from a secrets manager or the environment,
   and keep `.env` files out of git.
2. Give each service its own key, with the smallest scope that works: read-only when it only reads.
3. Prefer short-lived tokens. Rotate long-lived keys on a schedule, and when someone leaves.
4. Store the tokens you issue only as hashes, like passwords.
5. Scan commits, CI logs and chat for secrets, and block pushes that contain one.
6. When a key leaks, revoke it first, then clean the history. Deleting the commit is not enough.

## Common mistakes

- Trusting a private repository. GitGuardian finds internal repositories about six times more
  likely to contain secrets than public ones.
- Keys in MCP and agent config files, copied from a quick start guide.
- One shared key for every environment and service.
- Secrets pasted into tickets and chat during an incident.
- Secrets in error messages or analytics events.

## Example

This site gives tokens to the agents that people connect to their map. Each token is a random
256-bit string, stored only as a SHA-256 hash, so a copy of the database holds no working token.
Access tokens last one hour. Refresh tokens last 60 days and change each time they are used. The
analytics API key is read-only, and comes from the environment or an ignored file, never from the
code.
