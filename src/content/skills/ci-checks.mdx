## Why it matters for a product engineer

CI checks catch problems before review and before users do. But they run on every change, so their
speed and reliability set the pace for the whole team. A slow or flaky CI makes people wait, batch
their changes, or ignore a red build.

## How to do it

1. Run the fast checks first: format, lint, type check and unit tests. Then the slower ones.
2. Set a target for CI time at p95, not the average, and measure each step.
3. Skip work that a change cannot affect: run only the related tests, and reuse cached dependencies
   when their inputs have not changed.
4. Track flaky tests. Fix them or set them aside, each with an owner.
5. Add checks for what reviews miss: security scans, performance budgets, accessibility and broken
   links.
6. Make a red main branch the team's first priority.

## Common mistakes

- A check that fails at random, so people run it again without reading it.
- New checks added, while slow or useless ones are never removed.
- Every test on every change.
- Checks that run only after the merge.

## Example

Shopify's core monolith had more than 170,000 tests, and its CI took 45 minutes at p95. The team
measured every command and found that 68% of the time went to work before any test ran: preparing
machines and building dependencies. They fixed a disk bottleneck that slowed containers. They
skipped database migrations when a hash of the migration files had not changed. And they ran only
the tests related to each change.
