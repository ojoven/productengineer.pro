## Why it matters for a product engineer

A boundary decides what each part of a system owns and how the parts talk to each other. Good
boundaries follow the product and its domain, so they rarely change. Bad ones, often drawn too early,
make every feature a negotiation between services. Engineers draw most boundaries while building,
often without noticing.

## How to do it

1. Draw a boundary where the responsibility changes, not where the code is large.
2. Ask what really needs a server, a database or a separate team, and keep the rest simple.
3. Define what crosses the boundary: an API, an event or an exported file, with an owner and a
   version.
4. Keep data private to the side that owns it. The other side asks for it through the interface.
5. Start inside one application. Move a part out only when its boundary has stayed stable.
6. Check how often a change crosses a boundary. If it is most changes, the line is in the wrong place.

## Common mistakes

- One service per database table.
- Two services that read and write the same tables.
- Boundaries copied from the organisation chart instead of from the product.
- No written contract, so each side guesses what the other sends.

## Example

This site is mostly static: every page is HTML built in advance, and readers without an account never
call a server. Only three things need one: accounts, synced progress and an MCP server for agents.
They live in a small separate API, and the web server sends it only those paths. The skills content
reaches the API as one exported file, so the two sides can change separately.
